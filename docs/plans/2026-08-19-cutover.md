# Cutover Implementation Plan — one process, for real

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Status:** written 2026-08-19. Task 1's configuration is authored (2026-08-20); its four machine steps, and Tasks 2–4, are not run.

**Goal:** make the composed host the thing people actually reach — on the game machine first, then on Render — and retire what it replaces: three launchd agents, three ports, three Caddy routes, Acquire's GitHub Pages deploy, its long URL, and four source repositories.

**Spec:** [`specs/2026-08-19-monorepo-single-host.md`](../../specs/2026-08-19-monorepo-single-host.md) — migration-sequence steps 9–11.

**Predecessor:** [`docs/plans/2026-08-19-composition-one-process.md`](2026-08-19-composition-one-process.md) — complete. `apps/host` exists, runs all three games on port 4000, and is tested; nothing deploys it yet. That is what this plan changes.

## What makes this plan different from the last three

**Every previous plan was safe because nothing it did was visible.** Phase 0, the monorepo, the composition — all of them ended with the same three services serving the same three games from the same three ports, and a mistake cost a test run. This one is the opposite: **every task is visible to someone else**, two of them cannot be undone by `git revert` alone, and one of them changes a URL people have bookmarked.

So the shape is different. Each task carries an explicit **rollback**, written before the task is run rather than improvised while something is down. Where a step touches live data it says so. Where a step is irreversible it says that too, and says what to check _before_ taking it.

## Order: the LAN first, and why that is not the spec's order

The spec lists Render as step 9 and the LAN as step 10. **This plan reverses them**, deliberately:

- The LAN cutover is **reversible in about a minute** — reinstall three agents, restore one config file — and nothing about it is user-visible outside your house.
- It gives you **an evening of real play** on the composed process before anything reaches production. Four hundred lines of tests are not the same evidence as three people on phones.
- The `/acquire` rename is **coupled to Pages retirement, not to the LAN**. The composed host mounts Acquire at whatever `BASE_PATH` says, and after Task 1 Caddy proxies everything to one port without naming any game — so the rename needs no LAN change at all, before or after. The two cutovers are genuinely independent in that direction.

The one cost of this order: the drift window against the four source repos stays open a little longer. It closes in Task 4.

## Global constraints

- **This clone is not the game machine.** Every script and plist assumes `~/Developer/game-host`; this checkout is `~/Developer/personal/game-host`, and neither Caddy nor the `/opt/homebrew/etc/game-host` symlink exists here. Task 1 is **configuration authoring** — write it here, run it there. Do not try to smoke-test Caddy or launchd locally, and do not "fix" the hardcoded paths.
- **The composed host must already be merged to `main`** and pulled on the game machine. Task 1 step 1 checks this rather than assuming it.
- **Do not touch `saves/` contents.** Task 1 relies on the directory names already matching (see below) and must not move, copy, or clean anything under it.
- **The `/acquire` rename and the Pages retirement are one commit.** Not one branch, one _commit_. Spec §7: a built client whose base disagrees with where it is served requests every asset from a path that does not exist, so whichever half ships second is broken until the other lands.
- **Nothing is deleted until its replacement has been observed working.** Old plists, old start scripts, the old repos: each is removed in the task _after_ the one that replaced it, never in the same one.

## Task 1: The LAN — one service instead of three

**Files:**

- Create: `start-host.sh`, `launchd/com.game-host.plist`
- Modify: `Caddyfile`, `README.md`, `PORTS.md`
- Delete (step 7, after the new one is observed working): `start-railbaron.sh`, `start-acquire.sh`, `start-marcopolo.sh`, `launchd/com.game-host.{railbaron,acquire,marcopolo}.plist`

**Status: the files are written, the switch is not thrown.** Steps 3, 4, 5 and
8 are configuration authoring and are done, in two commits — one additive
(`start-host.sh`, `launchd/com.game-host.plist`), one switching (the collapsed
`Caddyfile`, `PORTS.md`, `README.md`). Steps 1, 2, 6 and 7 can only happen on
the game machine and are a runbook, not a task.

**Pulling the second commit arms the switch**, but does not throw it: Caddy
re-reads its config only on restart, so the games keep working on 4001–4003
until `brew services restart caddy`. Do not restart Caddy for an unrelated
reason between the pull and step 6, or the front door will start forwarding to
a port with nothing behind it.

**Two deviations from the steps below, both decided while writing them:**

- **4001–4003 keep their rows in `PORTS.md`** (step 8 said to delete them).
  They are no longer hosted, but `npm run dev:server` still binds them every
  day, and a number a command binds is a number that can collide. Deleting the
  rows would free 4002 for the next thing to claim, and Acquire's `dev:server`
  would then fail on a machine where something else got there first, with
  nothing in the registry to explain why.
- **The three Vite dev proxies keep pointing at their own game's port**, not at 4000. Developing one game should mean running one game; the standalone boot
  path was deliberately preserved through the composition work so that keeps
  working, and repointing dev at the composed host would trade it away for a
  resemblance to production that dev does not need.

**The one thing that is already right, and must not be "fixed":** the composed host allocates `${DATA_DIR}/railbaron` and `${DATA_DIR}/acquire`, and the game machine already has `saves/railbaron` and `saves/acquire` — created by the two start scripts being retired. So `DATA_DIR="$HOME/Developer/game-host/saves"` finds every existing room **with no move at all**. This is the opposite of Render, where the directory is `games` and has to be renamed (Task 2). Do not rename anything here to "match" Render; they are already both correct.

- [x] **Step 1: Confirm the machine has what this needs, before changing anything**

```bash
cd ~/Developer/game-host
git pull                       # must include the composition work
ls apps/host/main.ts           # exists?
ls saves/                      # railbaron/ and acquire/ present?
lsof -nP -iTCP:4000 -sTCP:LISTEN   # must be empty
```

If `apps/host/main.ts` is missing, the merge has not reached this machine and nothing below will work. Stop.

- [x] **Step 2: Install and build, as the machine will actually run it**

```bash
npm install
npm run build                  # all three clients; a few seconds
DATA_DIR=$(mktemp -d) npm run start:host
```

Leave it in the foreground and check it by hand: `curl localhost:4000/health` reports three games, `curl localhost:4000/` is the menu, and each `/<game>/` serves its client. **Then stop it with Ctrl-C** — the launchd agent and a by-hand run fight over the same port, and that fight is the oldest lesson in this repo's README.

**A scratch `DATA_DIR`, not `saves/`, and this is not fussiness.** The three old services are still running during this rehearsal, and Rail Baron's is holding `saves/railbaron` while Acquire's holds `saves/acquire`. Pointing the composed host at the same directory puts **two servers on one set of room files**: both restore the same rooms into separate memory, both write them back, and each store's atomic temp-and-rename cheerfully clobbers the other's last move. The file that survives is whichever wrote second, which is not a rule anyone can reason about.

So the rehearsal proves the process boots, builds, serves and menus — everything except reading the real saves, which is the one thing it must not do while something else has them open. The real `DATA_DIR` arrives with the plist in step 6, by which time the old agents are gone.

The same hazard rules out the tempting middle step of running all four agents at once to compare them side by side. Marco Polo would be fine — it persists nothing — but the other two would be two writers on one directory. If you want that comparison, give the composed host a scratch directory for it.

- [x] **Step 3: `start-host.sh`**

  One script replacing three. Copy the shape of `start-railbaron.sh` — the `set -eu`, the absolute path, the `mkdir -p`, the comment explaining why the path is absolute — and change what it does:

```sh
#!/bin/sh
set -eu
GAME_HOST="$HOME/Developer/game-host"
# One directory for every game's saves; apps/host allocates a subdirectory per
# game beneath it. Absolute, not relative: a service's working directory is
# wherever its plist says, and a relative path would resolve somewhere else
# and make every saved room appear to have vanished.
DATA_DIR="$GAME_HOST/saves"
export DATA_DIR
mkdir -p "$DATA_DIR"
cd "$GAME_HOST"
# Builds all three clients, then runs one process serving all three games,
# their sockets, and the generated menu on port 4000.
npm run build
exec npm run start:host
```

Keep the build in the script, as `start-railbaron.sh` did with `npm run serve`: a service that starts after a `git pull` should serve the code that was pulled, not the last build.

- [x] **Step 4: One plist**

  `launchd/com.game-host.plist`. Copy `com.game-host.railbaron.plist` verbatim and change exactly four things: the `Label` to `com.game-host`, the script name to `start-host.sh`, and both log paths to `/opt/homebrew/var/log/game-host.log`.

  Everything else stays and stays commented — the `/opt/homebrew/etc/game-host` symlink in the paths (so no username is baked in), the `node-bin`-first `PATH` (the x86_64-node-under-Rosetta lesson), and `KeepAlive`/`SuccessfulExit: false` (crashes restart, a deliberate `bootout` stays stopped).

- [x] **Step 5: The Caddyfile collapses**

  Nine `handle` blocks become one. Every game route, the menu root, and the three per-game redirects all go; the composed host serves its own menu at `/` and its own prefixes below that.

```caddyfile
http:// {
  reverse_proxy localhost:4000
}
```

Rewrite the file's header comment rather than deleting it. What is still true and still load-bearing: the prefix is never stripped, because each client is _built_ under its base path. What is no longer true: that the registry has a number per game. What is newly true: Caddy no longer knows the names of the games — adding one stops being a Caddyfile edit, which is the point of the whole exercise.

Keep the `/opt/homebrew/etc/Caddyfile` symlink note. The menu `root` block goes, and with it the `{env.HOME}` warning — record in the commit message that the lesson is retired rather than forgotten, since the symlink itself is still load-bearing for the plist.

- [x] **Step 6: Switch, in this order**

  The order is the whole step. Getting it wrong leaves three orphaned agents holding 4001–4003 that no script in the repo knows how to stop.

```bash
cd ~/Developer/game-host
./install-services.sh remove       # FIRST — while the old plists still exist
git pull                           # now the new plist and script arrive
./install-services.sh              # installs whatever launchd/ now contains
caddy validate --config Caddyfile
brew services restart caddy
```

`install-services.sh` globs `launchd/com.game-host*.plist` — **it needed one edit to get there**, made 2026-08-20 while running this step. The pattern was `com.game-host.*.plist`, which requires a segment between the label and the extension: it matched the three per-game plists and _not_ `com.game-host.plist`. Run unfixed, the sequence below would have removed three agents, installed nothing, and restarted Caddy onto an empty port 4000. The glob still only _removes_ agents whose plists are in the working tree, so the ordering stands: remove first, then pull.

- [ ] **Step 7: Verify through the front door, then delete the old files**

```bash
curl -s localhost/health          # three games
curl -s localhost/ | head         # the menu
curl -s localhost/railbaron/health
curl -s localhost/acquire-startups-m1/health
curl -s localhost/marcopolo/health
tail -20 /opt/homebrew/var/log/game-host.log
```

Then, and only then, delete the three start scripts and three plists in a commit of their own.

**And play a game.** Not a curl — an actual evening, three people, phones, all three games if you can. The composition suite covers what a test can see; it cannot tell you the room felt slow.

- [x] **Step 8: `PORTS.md` and `README.md` catch up**

  4001–4003 retire: delete those rows, leaving the composed host on 4000 and the three dev-client slots, which are unaffected — three Vite dev servers still coexist during development. Update the "known consumers" list: the Caddyfile no longer names a game, and the three per-game boot defaults are now dev-only.

  Then repoint the three games' Vite dev proxies at 4000, which the composition plan deferred to exactly here. Each `vite.config.ts` proxies `<base>/socket.io` to its own `400N`; nothing listens there any more.

  In `README.md`, the six-step "adding a game" checklist loses its Caddyfile and menu steps and gains "add one row to `GAMES` in `apps/host/host.ts`".

**Rollback**, if anything above misbehaves:

```bash
cd ~/Developer/game-host
./install-services.sh remove
git checkout <commit-before-this-task> -- Caddyfile launchd/ start-*.sh
./install-services.sh
caddy validate --config Caddyfile && brew services restart caddy
```

This works for as long as the old plists exist in history, which is forever. Saves are untouched by either direction — the same `saves/railbaron` and `saves/acquire` serve both arrangements — so a rollback loses nothing but the evening.

## Task 2: Render — the service points at this repo

~~Nothing user-visible changes in this task. Acquire keeps its long path, the Pages client keeps serving it, and the rename waits for Task 3.~~ **Wrong, corrected 2026-08-20 before running the task.** This is the online cutover, and it takes the Pages client down.

Acquire's Pages client sets `VITE_SERVER_URL`, which makes its socket path socket.io's bare default `/socket.io`. Render serves that today only because `SOCKET_PATH=/socket.io` is set, and that variable is read by Acquire's _standalone boot block_ — which the composed host does not use. `HostContext` carries no `socketPath` (`packages/host/contract.ts`) and `apps/host/host.ts` passes only `{app, httpServer, dataDir}`, so a composed Acquire always mounts at `${BASE_PATH}/socket.io`. There is no configuration that makes it serve both.

Measured live, and they are exact mirror images:

| | `/socket.io` | `/acquire-startups-m1/socket.io` |
| --- | --- | --- |
| Render today (old repo) | **200** | 404 |
| the composed host | 404 | **200** |

So deleting `SOCKET_PATH` in step 2 is not "tidiness, not risk" — it is already inert, and that is the problem. The moment Render builds from this repo, the Pages URL (live, and how online players actually reach Acquire) stops connecting.

**Consequence for the order.** Task 2 was placed before Task 3 because it was believed to be invisible. It is not, so the reason is gone — and running it first makes online players change URL _twice_: Pages → `/acquire-startups-m1/` → `/acquire/`. Doing Task 3's rename first makes it once. What changes here is still _which repository builds the server_ and _what it runs_; what is no longer true is that nobody notices.

**The live service, read 2026-08-19:** `srv-d3klnhnfte5s73diht90` / `acquire-multiplayer`, starter, one instance, auto-deploy on commit to `main`, health check `/health`, disk `dsk-d9rafvlbedkc73coe2k0` at `/var/data`.

- [ ] **Step 1: The disk move, as a guarded pre-deploy**

  Acquire's rooms are at `/var/data/games`; the composed host will look in `/var/data/acquire`. Set Render's **pre-deploy command** to:

```sh
sh -c 'test -d /var/data/games && mv /var/data/games /var/data/acquire || true'
```

A pre-deploy rather than an SSH session, and the reason is a timing trap worth stating: SSH needs a _running_ service, so a `mv` by hand races the old server, which writes by path and would simply recreate `/var/data/games` underneath you. A pre-deploy runs with nothing serving. The `test -d` guard makes it idempotent, so it is safe on every subsequent deploy until you remove it — which Task 4 does.

**This is the one step that touches live player data**, and the data mattered — decided 2026-08-20: _"let's keep any games in /var/data."_

**It cannot work as written, and the reasoning above is backwards.** Run 2026-08-20: the pre-deploy reported success and the rooms never moved.

**A pre-deploy command cannot see the persistent disk.** It runs on separate compute, and the disk mounts only once the deploy is live ([Render docs](https://render.com/docs/disks)). So `/var/data/games` did not exist in that environment, `test -d` was false, the `&&` short-circuited, `|| true` returned 0, and the deploy log showed a clean run. The mechanism chosen to protect the data was structurally incapable of touching it, and it reported success for exactly the same reason.

The trap in the original argument is worth keeping, because the argument was half right. It said: SSH needs a *running* service, so a `mv` by hand races the old server, which writes by path and would recreate `/var/data/games` underneath you. True — **while the old server is what is running.** After the repo switch it no longer is: the composed host writes to `${DATA_DIR}/acquire` and never touches `games`. So the race the pre-deploy existed to avoid disappears at exactly the moment the cutover happens, and SSH becomes the correct tool rather than the dangerous one.

**Do the move at runtime, after the deploy, with the composed host serving:**

```bash
render ssh srv-d3klnhnfte5s73diht90
ls /var/data/games | head          # the rooms, untouched
ls /var/data/acquire | head        # anything created since the cutover
mv /var/data/games/*.json /var/data/acquire/
rmdir /var/data/games
```

A merge rather than a rename, because `/var/data/acquire` already exists by then and may hold rooms created since. Then **restart the service** — rooms are restored at boot, so files moved under a running host are not seen until it starts again.

Verify by opening a pre-move room. A 200 from `/health` proves nothing about it — and here, neither did a pre-deploy that exited 0.

- [ ] **Step 2: Change the service, all in one edit**

  | Setting           | To                                           |
  | ----------------- | -------------------------------------------- |
  | repo              | `github.com/petroleumjelliffe/game-host`     |
  | branch            | `main`                                       |
  | build command     | `npm install --include=dev && npm run build` |
  | start command     | `npm run start:host`                         |
  | pre-deploy        | the guarded `mv` from step 1                 |
  | health check path | `/health` — unchanged                        |

  Environment: **add** `DATA_DIR=/var/data`; **delete** `GAMES_DIR` and `SOCKET_PATH`; **keep** `NODE_ENV=production`.

  Three of those are load-bearing in ways that are not obvious:
  - `--include=dev` is not decoration. `NODE_ENV=production` makes npm set `omit=dev` (verified: `npm config get omit`), and `vite`, `typescript`, `@vitejs/plugin-react` and Acquire's `tailwindcss`/`postcss`/`autoprefixer` all live in `devDependencies`. Without the flag the build fails on the first Vite invocation. It has never mattered before because Render never built a client — Acquire's came from Pages.
  - `NODE_ENV=production` **stays**. It is what keeps Acquire's `/dev/rooms` seeding route out of production, and that route installs arbitrary game state.
  - `SOCKET_PATH` is already inert for the composed host — only Acquire's standalone boot block reads it — so deleting it is tidiness, not risk.

- [ ] **Step 3: Deploy and verify, before touching anything else**

```bash

curl -s https://acquire-multiplayer.onrender.com/ | head          # the menu
curl -s https://acquire-multiplayer.onrender.com/acquire-startups-m1/health
```

Then the thing the curls cannot tell you: **open a room that existed before the move and check its state is intact.** The disk rename is the only step in this plan that can lose something a person cares about, and a 200 from `/health` says nothing about it.

Note what has just become true and is easy to miss: Rail Baron and Marco Polo are now _on the internet_, at that origin, for the first time. Both were LAN-only. **Decided 2026-08-20: yes, both should be live.** Worth carrying forward rather than forgetting: both run `origin: '*'` with no auth, which is why tightening CORS is the next plan's obvious first item.

**Rollback:** point the service back at `acquire-startups-m1`, restore the build and start commands and `GAMES_DIR`/`SOCKET_PATH`, and reverse the pre-deploy (`mv /var/data/acquire /var/data/games`) before redeploying. The old repo is untouched until Task 4, which is why Task 4 is last.

## Task 3: `/acquire`, and the end of the Pages deploy — one commit

**The atomic one.** Spec §7: Acquire's `BASE_PATH` _is_ its GitHub Pages path, so the rename and the retirement cannot be separated. Whichever ships second leaves a client asking for assets at a path that does not exist.

- [ ] **Step 1: The rename, which is smaller than it sounds**

  `basePath.ts` is the one true source; Vite's `base`, the router basename, the PWA `start_url` and `scope`, the socket mount and the health twin all derive from it. The literal appears in exactly three places: `basePath.ts`, `server/clientOverWire.test.ts` (a hardcoded socket path), `src/pages/HomePage.test.tsx` (a hardcoded route). Grep before trusting that list — it was written before the monorepo.

- [ ] **Step 2: The permanent redirect**

  In `apps/host`, `/acquire-startups-m1/*` → `/acquire/*`, **preserving the suffix** so a shared room link keeps working. Two lines, kept indefinitely. Add a test to `apps/host/routes.test.ts` asserting that `/acquire-startups-m1/room/ABCD` redirects to `/acquire/room/ABCD` rather than 404ing — a redirect nobody tests is a redirect that quietly stops preserving the suffix.

- [ ] **Step 3: Retire Pages, in the same commit**

  **`.env.production` is already deleted** — pulled forward to 2026-08-20, during Task 1, and it did not have to wait. The atomicity this task insists on is about `BASE_PATH`: a client built under one base and served under another asks for every asset at a path that does not exist. `VITE_SERVER_URL` is not coupled to that, and Acquire's Pages client builds from the *old* repo, so deleting the file here could not reach it. What forced the issue: Task 1 put a composed host in front of a client that ignored it, so LAN Acquire served its pages from this machine and its sockets from Render. Every "LAN" game was a production game.

  Still to delete here: Acquire's `gh-pages` dependency, its `deploy` script, and `public/404.html` (the SPA fallback Pages needed; `apps/host` does that job properly now). Update `GAMES` in `apps/host/host.ts` if the directory name reads oddly beside the new path — the _directory_ is already `acquire` and does not change.

  Leave **Rail Baron's** Pages deploy alone. It is a client-only offline companion for use at the table, a different product from the hosted game, and it costs nothing to keep. It still owes the monorepo a root workflow with a path filter, which the composition plan flagged when it deleted the inert copy.

- [ ] **Step 4: Verify the things that break quietly**
  - `/acquire/` serves the game with **every asset resolving** — check the network panel, not just that the page renders; a cached bundle can hide a broken path.
  - `/acquire-startups-m1/room/ABCD` redirects rather than 404s.
  - A browser holding a **stored identity from before the rename** still rejoins its room. `createIdentityStore('acquire')` keys on the app id and never the path, so this should hold — verify it rather than trust it, because it is the difference between a rename and a data loss.
  - An **installed PWA** opens in a browser tab instead of standalone, and still works. That is the known, accepted cost (spec §7): the app is scoped to the old path, following the redirect takes it outside its own scope, and a reinstall fixes it. Confirm "degrades" rather than "breaks".

**Rollback:** `git revert` the single commit and redeploy. Pages is recoverable — the `gh-pages` branch survives a revert — but anyone who reinstalled the PWA at the new path during the window will need to reinstall again. This is the least reversible task in the plan, which is why it is third rather than first.

## Task 4: Archive, and stop the drift

Only after the LAN and Render have both run on the monorepo for long enough that you would have noticed a problem. A week of ordinary use is a reasonable bar; an evening is not.

- [ ] **Step 1: Remove the pre-deploy `mv`**

  It is idempotent and harmless, but it is also a one-time migration masquerading as configuration. Delete it once `/var/data/acquire` exists and has been read from.

- [ ] **Step 2: Archive the four repos on GitHub, read-only**

  `railbaron`, `acquire-startups-m1`, `marco-polo`, `multiplayer-game-lobby`. This is the step that actually ends the risk of editing the wrong copy — until it happens, four repos still look live and one of them still has a Render service pointed at it in its own README.

  **Check first that nothing still deploys from them.** Rail Baron's Pages deploy runs from its own repo and is _staying_, per Task 3 — so archiving Rail Baron's repo either kills that deploy or must wait for the monorepo workflow that replaces it. Resolve that before archiving, not after.

- [ ] **Step 3: The clone on the game machine**

  `~/Developer/railbaron`, `~/Developer/acquire-startups-m1`, `~/Developer/marco-polo` are no longer referenced by any script. Removing them is optional and safe; leaving them is a trap for a future by-hand session that edits the wrong tree. Prefer removing.

## Deliberately not in this plan

- **A linter/formatter.** Deferred three times now. It should land as its own commit between this plan and whatever comes next — a whole-repo reformat inside a cutover makes the diff unreviewable and the bisect useless.
- **Compiling `apps/host`.** Three servers plus two shared packages are transpiled by `tsx` at every cold start, on every Render restart. It is also what would retire the dev/production dependency question properly — a compiled server needs no toolchain at runtime. Measure first; the spec says so and it is still right.
- **A shared `packages/room-store`**, which would give Acquire the `settled()` it lacks (so `close()` could drain in-flight saves) and Rail Baron the `quarantine()` it lacks, in one move.
- **Tightening CORS.** Both games run `origin: '*'`. This plan finally creates the single public origin that makes narrowing it easy — which makes it the _next_ plan's obvious first item, not this one's last.
- **A shared remembered name.** `createIdentityStore` keys `${appId}.name`, so a player types theirs once per game; one origin makes a single `lobby.name` possible. A real game-night nicety, and only possible after Task 3.
