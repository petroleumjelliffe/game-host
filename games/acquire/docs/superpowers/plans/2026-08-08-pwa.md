# The PWA — plan

**Design:** [../specs/2026-08-08-pwa-design.md](../specs/2026-08-08-pwa-design.md) — read it first;
the rulings (standalone, next-launch updates, no phone view, no dev routes in prod) live there.
**Branch:** `revamp/pwa`, off `main`.
**Parallel-safe with:** `revamp/aqua-titanium-reskin` — see the design's conflict table. The only
shared file is `StaleClient.tsx`; whoever merges second reapplies a small change.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or
> superpowers:executing-plans. Verify in a real browser at every step that claims one — jsdom has
> no service worker, no manifest, and no install surface, so a green suite proves almost nothing
> here.

## Task 1 — `/catalog` and `/scenarios` leave the production build

Standalone and first, because it shrinks what every later task must cache, and it is the one task
another workstream could trip over.

- Guard both routes in `src/App.tsx` with `import.meta.env.DEV`. Vite folds the condition on
  build, so the routes *and their lazy chunks* (golden data included) are not emitted.
- Strengthen `npm run check:bundle`: it currently greps `dist/assets` for vitest; add a grep that
  fails if any emitted chunk contains golden-game markers (e.g. `ALL_GOLDEN_GAMES` or a golden
  title string). Prove it can fail: remove the `DEV` guard, build, watch it go red.
- `verify-layout.mjs` keeps working untouched — it drives a dev server, where the routes exist.

**Verify:** `npx vite build && npx vite preview`; `/catalog` 404s (the SPA fallback renders the
app shell, so "404" here means no catalog content and no catalog chunk in `dist/assets`). Dev
still serves both. Full gates.

## Task 2 — manifest and icons, generated from tokens

- A build-time generator (a small script, run from `npm run build` via `prebuild` or a Vite
  plugin) writes `public/manifest.webmanifest`: name, `display: standalone`, `start_url` and
  `scope` from the same base path `vite.config.ts` uses, `theme_color`/`background_color` **read
  from `src/game/tokens.ts`** — never typed by hand, so the reskin's palette flows through on its
  next build.
- Maskable icons (512/192 + apple-touch). Static files are fine; colour-derived generation is not
  required for the icon *art*, only the manifest colours.
- `index.html` gains the manifest link, `theme-color`, and the `apple-mobile-web-app-*` tags.

**Verify in a real browser:** Chrome DevTools → Application → Manifest shows installable with no
warnings; the computed `theme_color` equals the token value at runtime.

## Task 3 — the service worker

- Plain hand-written worker (`src/pwa/sw.ts` compiled by Vite, or `public/sw.js` if simpler —
  decide by what keeps the build unexotic; no Workbox unless it earns its dependency).
- Precache: `index.html`, emitted JS/CSS of the main entry, manifest, icons. The precache list
  comes from the build (Vite's manifest output), not a hand-maintained array.
- Runtime: network-first for navigations, cache-first for hashed `/assets/`.
- **No `skipWaiting` on install** — next-launch activation is the ruling. The waiting worker
  activates on the next open, or explicitly (Task 5).
- Registration is production-only and after load, in `src/main.tsx`.

**Verify in a real browser:** build + preview, install, kill the network (DevTools offline),
relaunch — the shell paints. Then the test that catches hand-maintained-list rot: change one
source line, rebuild, confirm the new hash precaches and the old cache is pruned.

## Task 4 — offline tells the truth

- **Prediction to verify first:** offline pass-and-play should already work end to end once the
  shell is cached — persistence is `localStorage` and the engine is local. Drive it: install, go
  offline, play a full turn, kill the app, relaunch offline, confirm the Continue card resumes.
  If anything fetches at runtime and breaks this, that finding reshapes the task.
- The mode chooser: when `navigator.onLine` is false (and on the `offline`/`online` events),
  Online is disabled with the existing honest wording — reuse the
  `No network — waiting for this device to reconnect` vocabulary, do not invent a second phrasing.
- Online routes reached while offline show the same state they already show on a dropped socket;
  nothing new to build, verify nothing new is *needed*.

**Verify:** the drive above, plus airplane-mode on a real phone if available.

## Task 5 — the update path, and the one dangerous button

The riskiest task; do it last, alone, and by hand.

**The install base is zero, and that changes the deadline, not the care** (owner, 2026-08-08:
*"it's not installed anywhere yet so no one will be left behind"*). While nobody has installed,
the worker can be shipped, torn down and reshaped across deploys freely — Tasks 1–4 can even merge
and deploy ahead of this one with no risk. What does not relax: a broken updater is the one bug
that survives its own fix being deployed, because the update path is the only way a fix reaches an
installed device. So the hard cutoff is **before the first real install** — Task 5 verified by
hand, on a real installed app, against a real refusal — not before the first merge.

- An update prompt: when a new worker is *waiting*, surface a quiet "Update ready — restarts the
  app" affordance in the lobby (never mid-game; the panel is not the place).
- `StaleClient` gains **Update now**: unregister/skip the waiting worker, clear the shell caches,
  `location.reload()`. This is the path that must get *past* the worker — an ordinary reload can
  be served the cached shell again and loop.
- The failure worth engineering against: **a wedged install** — cached shell, incompatible
  protocol, reload loops. Write the recovery order (activate waiting worker if any → clear caches
  → reload) so there is no state from which the button does nothing.

**Verify by hand, on a real installed app:** install at version N; deploy a `PROTOCOL_VERSION`
bump to prod (or simulate with a local server refusing N); open the installed app; see
`StaleClient`; press Update now **once**; land in a working client. Then the background path:
deploy an asset-only change, confirm nothing prompts mid-game and next launch runs the new build.

## Task 6 — gates, whole-branch review, and the record

- Full gates. `verify-layout.mjs` untouched and green.
- **Review the whole branch, not per task** — the standing rule.
- CLAUDE.md: dev-surfaces line gains "dev builds only"; deployment section gains the

## Explicitly out of scope

The phone view (superseded ruling, recorded in the design), any offline story for online rooms,
push notifications, background sync, and `localStorage`-to-IDB migration for iOS eviction — the
last is noted in the design as a known platform weakness, accepted.
