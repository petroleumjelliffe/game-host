# Friends: invite the people you've played with, no address required

**Status:** designed 2026-09-02, not yet planned.
**Home:** this repo, same reasoning as its parent. This spec layers onto
[2026-09-01-email-invites-and-seat-keys.md](2026-09-01-email-invites-and-seat-keys.md)
and assumes its machinery (reserved seats, invite tokens, the seat key);
nothing here stands without it. It adds **no host contract changes**: the
parent spec's two capabilities are enough, and the friend layer lives
entirely inside `packages/notify` and client UI.

## The property being bought

**Inviting someone you've played with is picking a name, not typing an
address.** The system reaches that person through their own registered
notification settings, push or email per their prefs, and the inviter
never sees, needs, or can extract the address. Email invites stay for
first contact with someone the system has never met; friends cover
everyone else, which after the first game night is nearly everyone.

The privacy stance is the point, not a side effect: the game surfaces
show only what a table already shows, the name someone played under.
Addresses live where they already live, in notify's profile records, and
never cross to another player.

## Current state (what "friend" can even be made of)

The only cross-game, cross-room identity anywhere is the notify profile:
`profileId = sha256(playerKey)`, holding channels and prefs
(`packages/notify/records.ts`). The lobby's identity is per-room seats;
its names are per-room roster entries plus the client-side shared
`lobby.name` key. Nothing durable connects "this person in room A" to
"this person in room B" except the profile.

So "players you've played with" must mean: **profiles that were bound to
seats in a room where your profile was also bound.** That definition has
a built-in alignment worth stating: someone appears in your list only if
they set up notifications, which is exactly the population reachable
through "their registered notification settings." A player who never
touched notify is invisible to friend lists and also unreachable, the
same boundary twice.

Two gaps stand between that definition and a feature:

- **The history evaporates.** Co-presence exists only in
  `RoomRecord.bindings`, and `roomRemoved` deletes the record. A friend
  list cannot be derived on demand; it has to be written down while the
  room still exists.
- **Notify knows no names.** A list of anonymous profile hashes invites
  nobody.

## The design

Five pieces. The ledger (2) is the substance; the rest feeds it a name
(1), reads it out safely (3), spends it (4), or reserves its future (5).

### 1. Profiles get a display name

`ProfileRecord` grows an optional `name`. The client stamps its shared
`lobby.name` onto the existing bind call (`POST /notify/bind` grows a
`name` field), last-writer-wins, trimmed, length-capped, same guard
discipline as every other record field. The alternative, a contract
capability asking games for roster names, was considered and declined:
more plumbing across the host boundary for a name that dies with the
room, when the client already holds the durable one and is already
making the call.

The name is what other players' pickers show. It is exactly as public as
sitting down at the table was, and it refreshes on every bind, so a
rename propagates the next time its owner plays.

### 2. The co-player ledger

When `bindSeat` binds a profile into a room, notify writes reciprocal
**contact entries** between that profile and every other profile already
bound there (claiming an invite runs the same bind path, so invited
players enter the ledger too). Both directions are written at the later
bind, when both profiles are known.

```
ContactRecord {
  contactId,      // random, minted per owner; see section 3
  profileId,      // the other player; internal, never leaves the server
  name,           // their profile name as of the last shared bind
  gameId,         // where we last played
  lastPlayedAt,
  status,         // 'played' | 'pending' | 'accepted' | 'blocked'; see section 5
}
```

Entries live on the owning `ProfileRecord` (`contacts: ContactRecord[]`),
deduped by `profileId`: a re-encounter updates `name`, `gameId`, and
`lastPlayedAt` rather than appending. The list is capped (100,
oldest-`lastPlayedAt` evicted first), because it is a "people I might
invite" list, not an archive.

One wart accepted with eyes open: a person with two profiles (the iOS
storage-bucket split in the PWA spec, or a cleared browser) appears
twice, under the same name. The parent spec's out-of-scope ruling on
profile merging covers this; the ledger keys off profiles precisely so
that a later merge is a data migration here, not a rethink.

### 3. Reading the list out

`POST /notify/contacts { playerKey }` returns, per entry: `contactId`,
`name`, `lastPlayedAt`, the game's title, and `reachable`, a boolean
meaning "at least one enabled channel exists" (confirmed email or a push
subscription, prefs respected). Never an address, never a `profileId`,
and never *which* channel.

`contactId` is a per-owner random handle rather than the `profileId`
itself, deliberately: `profileId` is stable and global, so exposing it
would let any two players correlate their lists ("is your Alice my
Alice?"), a small leak but a free one to close. The server resolves a
`contactId` only within the caller's own ledger; someone else's
`contactId`, or a fabricated one, gets the same shaped "no", mirroring
the parent spec's non-probe rule.

### 4. Invite by contact

The parent spec's invite endpoint grows a second target shape:

```
POST /notify/invite { playerKey, game, roomId, playerId, token, email }     // parent spec
POST /notify/invite { playerKey, game, roomId, playerId, token, contactId } // this spec
```

Everything up to delivery is the parent flow verbatim: the inviter
proves their own seat via `verifySeat`, notify asks the game to
`reserveSeat`, mints the invite token, records the invite.
`InviteRecord.email` becomes a discriminated target:
`{ kind: 'email', address }` or `{ kind: 'profile', profileId }`.

Delivery is where the shapes diverge. A profile-targeted invite fans out
through the target profile's channels per their prefs, **immediately**:
no debounce and no presence check, because those exist to avoid
notifying someone already looking at the room, and an invitee has no
room to be looking at. Push says "Pete invited you to Acquire, room
QZWXV" and deep-links the room URL with the invite token; email is the
parent spec's invite mail to the already-confirmed address. A new
payload kind joins `TurnPayload` in `channels.ts`; the shared service
worker from the PWA spec needs nothing new, a push with a URL is a push
with a URL (scope-tagged routing applies as designed there).

The link stays bearer, and claiming stays the parent spec's claim,
unchanged. The target profile is who gets *told*, not a restriction on
who can claim; restricting claims to one profile would break exactly the
multi-bucket devices the seat key exists to serve.

No consent question arises that email invites had to answer: the
double-opt-in already happened when the address was confirmed, the
invite respects `prefs` and the unsubscribe state like any turn
notification, and section 5 reserves the harder social consent question
without answering it.

Two refusals, both cheap and honest (the contact list is the caller's
own data, so unlike key redemption these are not probes): `unreachable`
when no enabled channel exists (refused *before* reserving a seat, so
nothing dangles), and `blocked` per section 5. The picker should grey
unreachable entries rather than hide them, so "why can't I invite Sam"
has a visible answer.

Abuse limits, indicative numbers: an inviter cap of 20 invites per UTC
day across both target shapes (same counting shape as the email
confirmation limit), and at most one outstanding invite per (room,
target), where re-inviting resends rather than re-reserving.

### 5. The accept/reject stub, deliberately hollow

`status` on `ContactRecord` ships with one live value, `'played'`, and
three reserved ones: `'pending'`, `'accepted'`, `'blocked'`.

The v1 rule is that having shared a table is consent enough to be
invited back: a person you sat with can tap you on the shoulder. The
enum plus one enforcement point (invite-by-contact refuses a `'blocked'`
entry) is the entire stub. No request flow, no accept/reject UI, no
endpoints, no way to *reach* `'blocked'` yet. When friend requests earn
their keep, adding someone unplayed-with, consent-gating invites,
muting a specific person, they arrive as status transitions and
endpoints over this record, not as a schema change. Until then the
invitee's real defenses are the ones that already exist: channel prefs
and unsubscribe.

## Testing

- Ledger: reciprocal entries written at bind, claim-path binds included;
  entries survive `roomRemoved`; dedupe-and-refresh on re-encounter; the
  cap evicts oldest-played first.
- Listing: the wire shape provably contains no address and no
  `profileId` (assert on serialized output, not intent); `reachable`
  tracks prefs and channel state.
- Resolution: another profile's `contactId` and a fabricated one produce
  the same shaped refusal.
- Invite by contact: fans out through the fake channels per prefs; sends
  immediately (no debounce timer involved); `unreachable` refused before
  any seat is reserved; `blocked` refused; inviter day-cap; resend does
  not double-reserve.
- Wire tests still cannot prove possession properties (the CORS note in
  CLAUDE.md); assert on record state and response shapes, as the parent
  spec's tests do.

## Out of scope, deliberately

- **Friend requests and accept/reject.** The stub above, and nothing
  more, until something needs it.
- **Adding a friend you haven't played with.** No usernames, no search,
  no directory; that is an account system arriving sideways. The ledger
  grows by playing.
- **Profile merging.** Inherited from the parent spec; the ledger's
  duplicate-person wart is the cost, and keying everything off profiles
  is what keeps the eventual fix a migration.
- **Exposing which channel reaches a contact.** `reachable` is a
  boolean forever; "Sam has email but no push" is nobody's business.
- **Presence and social features.** No "online now", no profiles pages,
  no counts of games played together. It is an invite picker, not a
  social graph.
